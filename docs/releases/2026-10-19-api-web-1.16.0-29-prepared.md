## Kolejność przyszłego wdrożenia

Wykonać aktualną procedurę `DEPLOY.md` z trzema plikami Compose (bazowy + overlaye
push i mentor) i kontrolą
`config --quiet`. Przed promocją: zachować aktualne obrazy, wykonać świeży backup,
sprawdzić checksumę i izolowane odtworzenie oraz serializowaną kontrolę migracji.
Tych operacji produkcyjnych nie wykonywano podczas przygotowania wydania.

**Nie aktualizować API i web równocześnie jednym poleceniem.**

1. Najpierw API (i sender z tym samym obrazem), po wymaganych kontrolach backupu
   i migracji. Potwierdzić health i właściwy obraz nowego API.
2. Dopiero potem web z dokładnego obrazu wskazanego powyżej.
3. Sprawdzić publiczne metadane wersji, packageId i hashe zasobów oraz istniejące
   współdzielone witryny. Authenticated smoke wymaga aktualnych danych operatora;
   nie używać znanego nieaktualnego hasła bootstrap ani resetować go do testów.

Nowy klient pomija `measurement.data` podczas korekty zsynchronizowanego wpisu.
**Stare API nie obsługuje tego kontraktu.** Sam rollback web nie dowodzi, że nie
ma już klientów 1.16 w otwartych kartach lub cache. Nie cofać API do starej wersji
przy takich klientach; preferować poprawkę roll-forward albo utrzymanie API
obsługującego nowy kontrakt. Nie usuwać storage, outboxa lub kwarantanny.

Stare podglądy kontekstu Mentora są celowo odrzucane; wymagają odświeżenia
i ponownego potwierdzenia. Nie wykonywać mieszanego rolloutu instancji z różnymi
kontraktami selektora. Przy rzeczywistym odtworzeniu bazy obowiązuje również
rotacja `MENTOR_CONTEXT_GENERATION` opisana w `docs/mentor.md`.
